The Threads tab, where you write freely with no AI in the loop. The old page was four identical bordered rectangles in a column — chips, segment, search, then thirty atom cards — so every element had equal weight and nothing led; and at its foot sat a fake AI panel whose "Blackrose noticed" block made zero LLM calls. This rebuilds the page around a real writing surface as the primary action. Everything is live: type and keep it, search, tap filters, drag the theme strip, click a theme word.

A Index open ↗

No boxes at all. Memories sit on a ruled column with a serif date in the margin, like a printed ledger. Filters become one line of text with the active word inked; search becomes a rule you write on. Writing opens the page as a blank line — "New line" — and keeping it numbers it into the ledger.

The writing surface

The old panel was Notes / [Add a private note…] / Save note / Refresh / BLACKROSE NOTICED / "Themes settle around career pressure…" / Intention · Morning · Balance / Keep this as a note. It was a fake AI feature:

  • "Blackrose noticed" made zero LLM calls. It is a string template (generateMemoryNoteSuggestion, services/memory/localMemory.ts) that concatenates 180 characters of your own memory text and wraps it in canned therapy-speak — which is why it reads as three sentences jammed together with no grammar.
  • It still says "Rosebud" — the retired brand — and a test locks the string in (__tests__/services/localMemory.test.ts).
  • "Refresh" was a no-op. The suggestion is a pure function of the atoms, and refresh() already reruns it on every change. Same input, same string, forever.
  • "Keep this as a note" did nothing. It saved at layer: 'note', which topAtoms() then filters out — so keeping a suggestion could never influence the next one.

This page is where you write freely, with no AI in the loop. So the honest replacement is a real writing surface that is the page's primary action rather than a footnote below thirty cards. You write; a local matcher shows how it will be filed; you keep it. The matcher is plain word-boundary matching against a shared theme vocabulary — deterministic and predictable — and when it recognises nothing it says so instead of generating an observation. There is no Refresh because there is nothing to recompute, and no "Keep this as a note" because this is the note.

The content model

The cards showed real extraction output: "Recurring theme: the user returns to calm mornings…" with tags #recurring #theme #user. Four failures, none of them layout:

  • Leaked machine prose. "Recurring theme:" is the extraction prompt's own vocabulary coming back out of the model. memoryAtomExtraction.ts already forbids it; nothing validates the result, so it ships.
  • Third person. "the user returns" — the app talks about the writer to the writer, while the rest of the product says "What Blackrose holds for you".
  • Title equals content. Both fields carried identical text, so every card spent two lines saying one thing. Here title is the claim and body is the evidence, so they add rather than repeat.
  • Tags as artifacts. #recurring #theme #user is bookkeeping, not themes. Real themes are what the graph clusters on, so they are set as words and drive the filters and the strip.

The cards also show three things the old card threw away even though the atom already carried them: provenance ("from A week that got away from me"), confidence as a word and a meter, and recurrence ("returned 5×") from accessCount.

The dates

Each memory carries a serif date column in the margin — month over day. The month is dropped on a repeat of a day already shown above it, which is how a printed ledger handles continuation, so the eye reads one date per group instead of a wall of repeated months. Today's date is inked and carries a short rule beneath it.

These are write dates, never event dates — the clock doctrine. A memory written on the 19th about a Tuesday in August is filed on the 19th. The list header says "Written" for exactly that reason.

The drifting theme strip

The strip under the portrait drifts slowly, and it is also a normal scroll container you can drag left and right. Those two cannot both own the offset, so the drift drives scrollLeft rather than a transform — one mechanism, and the reader keeps full control of it.

Seamlessness rests on the content being periodic: the track holds N identical runs of the same words, so the offset scrollLeft + runWidth renders exactly the same pixels as scrollLeft. That makes the wrap invisible — and it means normalising the offset after a manual scroll is invisible too. N is computed, not hard-coded: we need maxScroll >= runWidth, and with a short theme list in a wide frame two runs are not enough, so the strip could never reach its own wrap point and the drift would jam against the end.

  • Any interaction hands control over. Hover, focus, wheel, touch or drag pauses the drift; it resumes after a beat of quiet, resynced from the DOM so it continues from wherever you left it.
  • Drag with a mouse only. Touch and trackpad already scroll natively, so the script fills the one gap the browser leaves on desktop. A few pixels of slop keeps an unsteady click a click, and a drag that ends on a word does not also fire that word's filter.
  • Hidden tabs do not drift — it would burn cycles for nobody and resume mid-word. Reduced motion keeps the strip fully scrollable; it only loses the self-propulsion.
  • Measured after the fonts load. A run measured in fallback metrics would put the wrap distance in the wrong place and show a jump at the seam, so the runs are re-measured once Playfair Display arrives.

Motion

Timings live in one place as tokens (--ease-out, --dur-fast 180ms, --dur-mid 320ms, --dur-slow 520ms). The list animates only on arrival, never on every keystroke: a search re-filter fades the whole set as one block rather than staggering items, because the list is a document, not a dashboard. Keeping a memory gives it a one-shot arrival — a short wash and a rise — and nothing loops.

Tokens

The locked palette (constants/blackrose.ts), the 12 / 16 / 28 radius scale, Playfair Display for titles and dates and Plus Jakarta Sans for body, and the bone / sage / rose layer families from the memory graph. Nothing here invents a token, and both schemes are painted — the strip, the list and the composer each carry their dark values.

What shipping this requires

The layout and writing surface are contained in MemoryHubScreen.tsx, components/memory/* and useLocalMemories. Deleting the fake block means removing generateMemoryNoteSuggestion, saveGeneratedMemoryNote, addGeneratedNote and refreshGeneratedNote, plus the test that asserts the "Rosebud" string. The content half needs post-model validation in the extraction path: reject or repair a leading "Recurring theme:" and any third-person "the user", enforce title ≠ content, and keep the theme vocabulary small and shared. Provenance, confidence and recurrence are already on LocalMemoryAtom — they only need to be rendered.
