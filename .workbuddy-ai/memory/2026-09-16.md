## R2.1 — the body-load cap (real bug, found while making the ledger deterministic)

- **The R1 byte instability was NOT ordering jitter.** Measured before changing anything: three
  ledger seeds produced the *same* file sequence and the *same* promoted set (13). The backlog order
  was deterministic all along (sequential staging + stable sort). The real cause was the pre-R2
  selection rule tie-breaking on `updatedAt`; R2's `rankMemoryFiles` plus pinned ledger capture dates
  fixed it. Bytes are now identical across runs: **6475 → 5630**.
- **The bug:** `getMemoryRecordsByIds` truncated to 10 ids — no name, no option, no signal in the
  return value. Victims: Dream (20 candidates → 10 bodies → the ten empty bodies all hashed alike →
  the per-thread duplicate collapse kept one each → **promoted 13 instead of 20**), supersession
  (50 → 10 files compared per thread), and **drive backup** (which paginates the manifest "so large
  file sets export fully", then exported 10 files regardless of store size).
- Fix: the cap is gone; `{ limit }` is now an explicit per-caller decision. `memory_get` keeps an
  explicit 10 and now *says* when it clipped. Dream's dedupe compares bodies **exactly** (not a
  31-bit hash) and never collapses on a body that failed to load.
- Ordering is by **capture date + id** (`listTmpFiles` oldest-first — decides Dream's promotion slice;
  `listMemoryFiles` newest-first — the recall recency fallback), never the wall clock.
- Regression tests: `__tests__/services/memory/memoryRecordLoad.test.ts` (4 tests, **all 4 red** with
  the cap restored — including that an explicit `limit: 5` used to return 10); `memoryFiles.test.ts`
  +2 ordering tests, both red under `updatedAt` ordering.
- **Supersession finally priced**, on a *separate* store (`probes/shared/restatementScenario.ts` +
  `probes/r2_supersessionDelta.ts`) — adding restatement pairs to the R0 ledger would perturb the
  frozen probe set. Same-store A/B: stale copy selected 1 → 0, `restated-topic` precision 0.5 → 1.0,
  context chars 874 → 553 (−36.8%), control thread byte-identical and intact.
- Gates: tsc clean · lint 0 errors (72 warnings) · check:design PASSED · `npm test` **1476 passed /
  0 failed** (283 suites, +11 tests vs the 1465 baseline). R0/R1/R2 headline metrics unchanged by all of it.
- Counting gotcha: a scratch `*.test.ts` under `.tmp/` is picked up by jest's testMatch and inflates
  the suite total (1477/284 vs the true 1476/283). Delete scratch tests before the final gate run.

## Conventions worth remembering (continued)

- **Price any pass as a same-store A/B**: seed one store, measure, apply exactly one pass, measure
  again. It is what makes "this mechanism helped" falsifiable instead of plausible.
- **Every mechanism that removes data needs a control that must survive.** Loosening supersession's
  criterion from restatement (0.9) to similarity (0.3) made *every* headline metric better —
  precision 0.5 → 1.0, context chars 1292 → 1010 — while deleting a real memory. A metric-only probe
  actively rewards over-firing.
- **Measure before diagnosing.** Two sessions in a row attributed a number to "wall-clock jitter";
  the first time it was wrong. A 3-run repeat of the same probe is cheap and settles it.
- **Never let a fixture inherit the wall clock.** Pin capture dates in the fixture, then order by
  them; otherwise a probe's byte-level numbers move between runs and every claim about them is soft.

## R2.2 — the backup path, and supersession's cost

- **Finding #5 measured, and it was worse than "unmeasured" — it was quadratic.** Supersession did
  `manifest reads = 2 x threads + 1`: `listMemoryFiles` paged the manifest per thread, then
  `getMemoryRecordsByIds` re-read it to resolve ids it had just been handed. At 200 threads over 5000
  files that is 401 full parses and **4.1s** — and time scaled with *thread count* at constant file
  count, so a journal that split into more topics got slower without storing more memories.
- Fix: one manifest read per pass, grouped in memory. Two additions to `memoryFiles`:
  `listAllMemoryHeaders()` (a batch pass needs its own door — `listMemoryFiles` caps `limit` at 50
  because it feeds prompts/UI) and `getMemoryRecordsForHeaders(headers)` (body loads with no manifest
  read, for callers that already hold headers). Result: 401 to **1** manifest read, 4053ms to
  **133ms**. Body reads stay at exactly one per file.
- The cost test asserts **storage work, not wall time** (1 manifest read; threads x per_thread body
  reads) so it cannot go flaky. Sabotage turns it red at 13 reads instead of 1.
- **Two more instances of the R2.1 bug class in the backup path:** (a) `buildMemorySnapshot` paginated
  the manifest "so large file sets export fully" then passed every page to the 10-id-capped loader, so
  a 500-file store exported 10 files; (b) `importMemoryFiles` sliced to 1000 *before* comparing
  lengths, so a 1001+ file backup threw "Backup contains invalid memory file records" — a corruption
  message for a size limit. Now validation and batching are separate (validate all, write in batches).
- **Retracted finding:** `restoreMemorySnapshot`'s atom slice of 400 is NOT a bug —
  `upsertMemoryAtom` prunes to `MAX_MEMORY_ATOMS` (400) on every write, so the slice is redundant. The
  real (small) issue was the duplicated literal; restore now references the constant.
- Gates: tsc clean · lint 0 errors (72 warnings) · check:design PASSED · `npm test` **1482 passed /
  0 failed** (284 suites). R2 metrics identical after the refactor.

## Conventions worth remembering (continued)

- **Measure storage work, not wall time, when pinning a performance property in a test.** Counting
  adapter reads is deterministic on any machine; a millisecond threshold is not.
- **When you remove a cap, go looking for its siblings.** Fixing the 10-id cap immediately exposed a
  second ceiling in the same call path that had been unreachable while the first one existed. Caps in
  one path tend to come in families.
- **Do not trust a suspicious slice until you have read what feeds it.** A literal 400 looked like the
  same bug again; it was an eviction policy upstream. Check the producer's bound before claiming the
  consumer truncates.
- **Heredocs in this environment expand template-literal interpolation even with a quoted delimiter.**
  Writing TS through `cat <<'EOF'` breaks on an interpolation containing a percent operator. Write such
  files with Python, or hoist the arithmetic out of the template literal first.

## R2.3 — two stacked fifties (the scan window was a lie)

- **Finding #7 fixed.** `SUPERSEDE_SCAN_LIMIT` bounded comparison to a thread's newest 50 files, so a
  restatement pair older than that was permanently invisible. Demonstrated: 12 and 50 files ->
  `superseded: 1`; 51, 62 and 202 files -> `superseded: 0`. Widened to **400** on measured grounds
  (raw `restatementRatio` sweep: 50 files = 1,225 comparisons / 2ms; 200 = 19,900 / 17ms; 400 = 79,800
  / 103ms; 3000 = 4.5M / 3.4s) and made residual truncation **visible** via a new
  `SupersedeOutcome.truncated` + a `console.warn`, instead of silently skipping.
- **The widening alone changed nothing.** `supersedeRestatedMemoriesInThread` read through
  `listMemoryFiles({ projectId, limit: SUPERSEDE_SCAN_LIMIT })` — and `listMemoryFiles` caps `limit` at
  50 (it feeds prompts/UI). **Two stacked 50s**: asking for 400 returned 50, silently, so the
  documented window was a lie about what the code did. Third instance of the R2.1 bug class (unnamed
  callee ceiling overriding a caller's explicit bound, no signal in the return value).
- Fix: `memoryFiles` gains `listMemoryHeadersForThread(projectId)` — one thread's non-deprecated
  headers, newest capture first, uncapped, one manifest read. Same cost as before; the bound is now real.
- **Half-applied guard closed:** the `_tmp` skip lived only in the whole-store pass, so the per-thread
  door could be aimed at the staging backlog and deprecate a staged file before Dream promoted it
  (it would vanish from `listTmpFiles`). The filter moved into `supersedeThreadHeaders`, which both
  entry points run.
- **My own bad assertion, worth remembering:** the tail test first asserted the live set through
  `listMemoryFiles({ projectId: 'desk', limit: 50 })` — but the pair is the *oldest two of 62*, so it
  is outside every page that door can return. The assertion would have "confirmed" a supersession
  without ever looking at the records in question. Now asserted through the uncapped door, with
  `toHaveLength(61)`.
- Sabotage, both single-test: door back through `listMemoryFiles` -> tail test red (`Expected: 1 /
  Received: 0`); `_tmp` filter removed -> `_tmp` guard test red (`Expected: 0 / Received: 1`).
- Gates: tsc clean · lint 0 errors (72 warnings) · check:design PASSED · `npm test` **1485 passed /
  0 failed** (284 suites). R2 metrics identical after the fix.

## Conventions worth remembering (continued)

- **A documented bound is only real if the door you read through honours it.** Widening a limit in the
  caller while the callee silently caps it lower is a no-op that reads as a fix — and it cost a full
  debugging cycle here. When you raise a constant, grep for every path that reads it.
- **Never verify a tail through a capped reader.** If the thing you are asserting on is at the far end
  of an ordering, a paged/capped read cannot see it, and a green assertion proves nothing. Assert
  through the door that can actually reach it, and pin the returned length so the door's own bound is
  under test.
- **The "silent unnamed cap" bug class is now at four instances** (10-id body load, 50-file scan window,
  50-file list cap under it, 1000-file import slice). Each one was a literal in a callee with no signal
  in the return value. When you find one, sweep the call path for the others before moving on.
