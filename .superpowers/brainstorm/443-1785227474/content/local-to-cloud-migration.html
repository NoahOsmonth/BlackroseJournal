Phase 0 · freeze the contract before moving data

Canonical source contract

  • Stable IDs for sessions, messages, entries, check-ins, and attachments
  • Original created, event, edit, finish, and deletion timestamps preserved
  • User-authored versus assistant-authored evidence distinguished
  • Content hashes and schema versions for idempotency and verification
  • Import provenance records the local key and source version

Architecture rules to replace openly

  • “Local-first memory” becomes “cloud-authoritative, offline-resilient”
  • The backend-local-only guard is replaced with cloud-boundary tests
  • Phone tools become authenticated backend memory operations
  • Storage-key ownership remains valid only for migration and offline state
  • Clear-history rules expand to cloud deletion and verification

Phase 3 · cloud rebuild and repair

Normalize time

Separate write date from event date, preserve timezone, and flag uncertain weekday references instead of inventing dates.

Resolve people

Build aliases and uncertain matches without merging two Jameses or treating every pronoun as the latest person.

Rebuild truth

Turn raw evidence into bitemporal claims, explicit supersession, episodes, open threads, and preferences.

Build search

Create full-text and vector projections across all sessions—not only the most recent local slice.

Build rollups

Session, day, week, month, and year views with links back to original messages and required counterevidence.

Report differences

Missing sources, duplicate sessions, stale facts, conflicting people, unsupported patterns, and failed jobs become explicit migration findings.

Rollback without losing new cloud conversations

Before cloud authority

  • Switch the account flag back to LOCAL
  • Local source data remains untouched
  • Cloud imports and projections can be discarded and rebuilt
  • No reverse migration is needed

After cloud authority

  • Cloud remains the source of newly written conversations
  • Disable advanced retrieval/agents, not cloud durability
  • Fall back to recent sessions and simple verified search
  • Repair forward or export an explicit local recovery bundle

Once new cloud-only messages exist, pretending the old local store is authoritative would itself lose data. Rollback therefore separates data authority from feature complexity.

Migration baseline

How should local memory become cloud-authoritative?

A

Mirror → rebuild → shadow → staged cutover — recommended

Idempotent upload, cloud reconstruction from raw evidence, silent retrieval comparison, explicit gates, per-user cutover, and a rollback observation window.

B

One-release cloud cutover

Upload once and immediately switch authority; fastest, but memory omissions, date errors, and deletion bugs appear only after local fallback is gone.

C

Long-term dual local/cloud authority

Maximum fallback, but permanent conflict resolution, duplicated bugs, mobile burden, and unclear truth ownership.
