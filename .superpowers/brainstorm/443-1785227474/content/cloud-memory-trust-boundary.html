Cloud Memory Trust Boundary

Cloud agents need temporary access to journal evidence, so “the server can never decrypt anything” would be dishonest. The maximum-quality design instead minimizes when, where, why, and for how long plaintext can exist.

Honest encryption model
On the phone
Device-keystore protected drafts, encrypted outbox, short-lived cache, secure session tokens.
→
In the Rosebud cloud
Per-user envelope encryption at rest; approved workloads receive just-in-time decryption for a narrowly scoped purpose.
→
At a model provider
Only the minimum evidence brief needed for that job, under verified retention and training-use controls.
Tradeoff stated plainly: true server-blind end-to-end encryption would prevent cloud search, curation, and agent reasoning unless heavy computation and indexing moved back onto the phone.

Workload authority · least privilege by job type

Live Turn Worker

Current conversation, response contract, and retrieved evidence brief. No unrestricted archive scan or deletion authority.

Memory Curator

Source sessions assigned to its job plus current relevant claims. Writes candidates through validation—not directly into truth.

Deletion Worker

Dependency traversal, tombstones, purge queues, and verification. Cannot generate chat responses or call general models.

Differential Worker

Separate opt-in permission, isolated key scope, minimal evidence, no durable-memory write capability, automatic expiry.

Provider policy gates

Required for journal evidence

  • Contract and configuration prohibit training on submitted content
  • Zero or explicitly bounded retention is verified—not assumed
  • Data region and subprocessors are known and versioned
  • Provider/model capability is allowlisted per job sensitivity
  • Requests and responses are never placed in ordinary application logs

Automatic provider exclusion

  • Unknown retention or training behavior
  • Weak tenant isolation or unresolved security incident
  • Model cannot meet structured-output and deletion requirements
  • Provider needs full identity or archive access
  • “Free model” economics require content reuse or opaque routing

Threats explicitly designed against

Cross-user retrieval

Tenant-scoped queries, database row policies, compound keys, authorization tests, and canary records.

Insider browsing

No plaintext admin explorer, purpose-bound access grants, audit alerts, and separate production roles.

Lost or rooted phone

Keystore-backed secrets, cache expiry, remote session revocation, and minimal local memory.

Queue replay

Signed job envelopes, stable idempotency keys, attempt bounds, and mutation-version checks.

Model exfiltration

No unrestricted tools, output DLP, bounded schemas, evidence minimization, and egress allowlists.

Backup resurrection

Deletion manifests, key retirement, backup inventory, expiry tracking, and restore-time tombstone replay.

Cloud security baseline

Which trust model should the detailed architecture adopt?

A

Zero-trust cloud compute with per-user envelope encryption — recommended

Purpose-bound decryption, isolated workers, provider gateway, no routine human access, short-lived sensitive data, and verified deletion.

B

Server-blind end-to-end encryption

Strongest server privacy, but cloud agents cannot search or curate plaintext; heavy memory computation must return to the device or trusted user hardware.

C

Standard SaaS encryption and admin access

Faster to build, but broad service access and routine plaintext debugging are not proportionate to intimate year-scale journal memory.
