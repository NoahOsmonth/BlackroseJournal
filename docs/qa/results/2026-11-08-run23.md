# QA run 23 — retry once when the AI writes nothing (#50)

A reasoning-only AI can spend an entire reply thinking and then produce no words. Before this round the app showed *"I could not put that into a reply…"* and stopped, leaving the writer to retype. Now it tries to get a real answer first.

## The order, and why it is that order

1. **Retry once with tools off.** A turn that ends in tool syntax or silence most often does so *because* tools are on. This costs nothing extra to set up.
2. **Retry once on a backup AI option.** Anyone who listed a backup did so for exactly this reason.
3. **Only then** show the plain sentence.

Each step runs at most once. A pure module (`utils/emptyReplyRetry.ts`) decides which step comes next; the caller performs it. That keeps every branch testable without a network.

## What counts as "no words"

Empty, whitespace-only, and invisible characters (zero-width space, BOM). Punctuation alone counts as an answer — *"..."* is something a person wrote.

## Tests

| Suite | Cases |
|---|---|
| `__tests__/utils/emptyReplyRetry.test.ts` | 14 — every step, order, blanks skipped in the backup list, no-tools-doubling, and a loop that proves the decision **always reaches give-up** |
| `__tests__/services/ai/emptyReplyRetryStream.test.ts` | 8 — drives the real `streamChat` with a mocked transport: no reply → one attempt; empty → tools off; still empty → backup option; all empty → the plain sentence; never more than three attempts; a transport failure reports once and does not retry |

**Sabotage-verified.** Forcing the retry loop off (`while (false && …)`) turned **5 of 6** loop tests red with the real output, then restoring turned them green. A test that cannot fail proves nothing.

## A bug my own refactor introduced — and the test caught

Moving the code into an inner attempt and an outer retry loop broke the failure path. `streamChatOnce` reports an error through `onError`, but the outer loop's `while` only guards the *empty* case, so a **failed** attempt fell straight through to `onComplete`. The writer would have seen *both* an error message and a reply bubble for one failure.

- I first assumed this was pre-existing. Checking `git show 07fde08:services/ai/ai.ts` showed the original caught the error and returned without completing — **this was mine**, introduced by the refactor, and the test written to cover the error branch caught it before commit.
- Fixed with an explicit `if (!attempt.ok) return;` and a comment saying why it matters.

That is the value of writing the test for the boring branch, not just the interesting one.
