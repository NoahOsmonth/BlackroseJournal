# QA run 29 — chasing the cold-mount storage reads (no change shipped)

This round measured, formed a hypothesis, tested it, and **the fix did not work, so I reverted it.** Recording the numbers so the next attempt starts from data instead of repeating this.

## What the bench says

`scripts/qa/route-mount-bench.mjs`, three samples, median:

| Route | Content visible | Longest task | Storage reads |
|---|---|---|---|
| Today | 1364 ms | 231 ms | 451 |
| Explore | 1291 ms | 236 ms | 382 |
| Insights | 1251 ms | 232 ms | 414 |
| Entries | 1354 ms | 240 ms | 410 |

All four are inside their budgets (≤2000 ms content, ≤300 ms task, ≤450 reads). **Nothing here is a defect yet** — Today sits at 451 reads against a 450 ceiling, which is why it looked worth chasing.

## What one cold mount actually does

Per-key counts from a single instrumented cold load of Today:

| Reads | Key |
|---|---|
| **23** | `blackrose_custom_ai_provider` |
| 17 | `goals` |
| 16 | `rosebud_local_memory` |
| 16 each | `rosebud_local_memory_shard:0/1/2` |
| 451 | total |

## Hypothesis, test, result

**Hypothesis:** 23 is exactly the length of `ACCOUNT_PRIVATE_EXACT_KEYS` in `legacyDataOwnership.ts`, and `hasLegacyStorage` reads those keys **sequentially**, one `await` each, on the boot path. So the ownership probe was the 23.

**Change tried:** batch those lookups with `Promise.all` so the probe costs one concurrent round instead of up to 23 sequential awaits.

**Result:** identical. `TOTAL 451`, and `blackrose_custom_ai_provider` still read 23 times. Reverted — it changed no behaviour, and `localStorage` is synchronous anyway, so there was no latency to win either.

The 23-matches-23 coincidence is therefore **not** the explanation. Unverified possibilities, not conclusions: the provider settings store being re-read per consumer, or a render loop re-invoking one loader. I did not prove which, and I am not shipping a guess.

## Why this is recorded rather than quietly dropped

A change that measures the same before and after is not an optimisation, and calling it one is how a bench stops being trusted. Three things are now cheap for the next attempt:

1. The bench numbers above are the current baseline for all four routes.
2. The per-key read counts name where the traffic is, instead of guessing at layers.
3. `Promise.all` over that key list is **already disproven** — do not retry it.

Next step is to make the owner of one duplicated read answer: instrument `loadCustomAiProviderSettings` and `listGoals` call counts directly rather than counting their storage reads, since a read count cannot tell many callers from one caller reading twice.
