# QA run 38 — Today loads the whole journal four times per tab switch

Round 32. The tab-switch budget had been missed since run 22, so this run went after the actual cause instead of the symptom.

## What the budget says

`docs/perf/ui-performance-rules.md`: a dock press must keep the **longest task ≤ 100 ms** and **storage reads ≤ 25**. Measured baseline:

| Pair | longest task | frame gap | reads |
|---|---|---|---|
| explore→today | 130 | 100 | 20 |
| insights→today | 117 | 100 | 20 |
| entries→today | 135 | 117 | 20 |
| today→explore | 117 | 100 | 0 |
| today→insights | 80 | 67 | 0 |
| today→entries | 138 | 117 | 19 |

Every `*→today` pair costs ~20 reads; every `today→*` costs ~0. The cost is mounting Today.

## Storage is not the bottleneck

Timed every key the screen reads: index 4.6 KB, shards ~4 KB each, parse **0.1–0.3 ms** each. Total under 2 ms. So the 130 ms is React render, not I/O — which means the read count was a symptom, not the cause.

## The real defect: four full journal loads

Instrumenting `Storage.prototype.getItem` during one tab switch counted **84 reads**, not the 20 the bench reported:

```
journal_entries ×4   shard:0..15 ×4 each (=64)   → 68 journal reads
intention_checkins ×3   intentions ×2   goals ×2
```

`loadStore()` reads the index plus all 16 shards on **every** call, and there is no cache. Four independent readers each paid that full cost for identical data:

1. `app/(tabs)/today.tsx` → `useJournalEntries()`
2. `hooks/today/useOnThisDay.ts` → `useJournalEntries()`
3. `hooks/journal/useGuidedPrompts.ts` → `useThisWeek()` → **`listEntries()` called directly**
4. one more instance mounting in parallel

That is rule R2 ("one read per collection") and R3 ("one hook instance per collection") both broken.

## Fix attempted, measured, and reverted

**Attempt:** a per-account store cache inside `journalStorage.ts`, invalidated in `saveStore` (the single chokepoint for all mutations) and on account change.

**Reads: 20 → 3. Journal reads: 68 → 0.** The cache worked exactly as designed.

**But it made frames slower, reproducibly:**

| Variant | total long-task time |
|---|---|
| no cache (baseline) | 421 ms |
| cache, synchronous hit | **617 ms** |
| cache, `await Promise.resolve()` | 261 ms |
| cache, `setTimeout(0)` | ~410 ms |

Cause of the regression: returning synchronously from a cache hit let all four hooks resolve in the **same tick**, so their `setState` calls batched into one large commit instead of being spread across microtasks. Adding a yield restored the spread.

**Then it broke backup restore.** Four tests failed:

```
localBackup › restores a backup and removes local keys absent from the snapshot
local backup delegated restore races › keeps a delegated restore bound to the account that started it
seedDemoData › auto-seed is a no-op when demo seed flag is false
seedDemoDataIfFirstLaunch › still writes deterministic memory atoms for the seeded rows
```

`services/backup/localBackup.ts` writes `@journal_entries` and its shards **directly**, bypassing `saveStore`. After a restore, `getJournalEntry('entry-1')` returned `null` — the cache served the pre-restore store. The demo seed has the same shape.

That is a data-critical path silently returning stale data. A cache whose correctness depends on every direct writer remembering to invalidate is the wrong shape for this codebase.

**Reverted the cache.** Read count is unchanged at 20; no measured gain was being given up.

## What was kept

`useThisWeek()` called `listEntries()` directly while a shared `useJournalEntries()` hook already existed — the one layering violation in the chain. It now derives its ledger with `useMemo` from the shared hook and re-exports that hook's `refresh`, so it no longer owns a second journal read path, its own loading state, or a swallowed `catch` that silently returned an empty ledger on error.

This does not reduce the read count on its own (it is one reader either way), but it removes the fourth independent load path and the silent-error branch.

## The correct fix, filed not rushed

The four readers need **one shared journal store with a subscription**, not a blind cache in the service:

- one module owns the parsed store and notifies subscribers on change
- every writer — including `localBackup` restore and the demo seed — goes through that module, so there is no invalidation discipline to forget
- reads become a getter, so N hook instances cost one parse and no stale window

That is a larger change than a round should absorb, and the backup-restore failure is the proof it needs designing rather than bolting on.

## Gates

2063 tests passed (exit 0), `tsc` 0 errors, lint 0 errors, `check:design` passed.

## Honest summary

This round did **not** move the tab-switch number. It replaced a guess ("Today is slow, maybe storage") with a measurement: the screen loads the entire journal four times, storage accounts for under 2 ms of it, and the naive fix trades a real data-integrity risk for no frame gain. The defect is now precise and written down.
