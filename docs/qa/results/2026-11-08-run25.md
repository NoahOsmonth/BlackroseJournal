# QA run 25 — a failed read no longer looks like an empty journal (#55, #25)

Round 18 could not tell whether the Recurring Themes card worked or its read was broken. The reason was two bugs, one in the app and one in my fixture.

## Bug 1 — the app reported a failure as a verdict about the writer

`loadIndexUnlocked` caught a failing `storageAdapter.getItem` and returned `emptyIndex()`. A storage failure and an untouched journal were **indistinguishable**, so the card told someone with a year of entries to *"write for a few more weeks"*.

Fixed by adding `readIndexUnlocked`, which returns the index **and** a status:

| Status | Meaning |
|---|---|
| `ok` | Read fine, has weeks |
| `empty` | Read fine, genuinely nothing written |
| `unreadable` | Could not be read — storage threw, or the stored index is damaged |

`listWeeklyRollupRead()` exposes it. The safe empty default stays, so nothing crashes; only the *reason* is now truthful.

## Bug 2 — my fixture, twice

The record key is `@rosebud_memory_rollup:<kind>:<periodKey>` and owner keys have **no leading `@`**. I seeded `@rosebud_memory_rollup:2026-W40` — wrong on both counts. The read was never broken; my data was in the wrong place, and because bug 1 existed, the app could not tell me.

That is the whole point of fixing bug 1 first: it converted a silent wrong answer into a signal.

## Verified live, both states

**With real rows in place:**

> CARD "**sleep 3 weeks, work stress 3 weeks**"
> runtime probe: `{status:'ok', rowCount:4, firstTopics:['work stress','sleep']}`

**After removing them:**

> CARD "Write for a few more weeks and the things that keep returning will show up here."

The seeded rows were removed afterwards; the journal is back to its real state. Confirmed by a follow-up read.

## Tests

| Suite | Cases |
|---|---|
| `__tests__/services/memory/memoryRollupRead.test.ts` | 6 — empty when nothing written, **unreadable when storage throws**, unreadable when the index is damaged JSON, unreadable when the shape is wrong, ok with real rows, month entries excluded |

**Sabotage-verified.** Reverting the catch to return `'empty'` turned the storage-throws test red; restoring turned it green. The other five stayed green throughout, so the suite tests the distinction and not just the happy path.

## The lesson, finally learned properly

Three rounds of seeded-storage confusion had one root cause each time: **I trusted my own fixture instead of making the app tell me what it saw.** Round 19 fixed the app's silence first, and the fixture error surfaced in one probe.

For storage features: make the read report its status, then seed, then look. In that order.
