# QA run 30 — the first-launch seed was calling the AI on every cold mount

Follows run 29, which measured a mystery and disproved its own hypothesis. This round found the real cause.

## The bug

`app/_layout.tsx` calls `seedDemoDataIfFirstLaunch()` on boot. That function has two sibling callers of the same worker, `seedDemoDataForAccount`:

| Caller | Runs inside `runWithDeterministicMemoryExtraction` |
|---|---|
| `seedDemoData()` (manual re-seed) | **yes** |
| `seedDemoDataIfFirstLaunch()` (boot) | **no** ← the bug |

`seedDemoData()` had the guard, added for DEF-013, with a comment explaining exactly why: the seeded rows carry their own analysis, so paying provider round-trips is pure waste. The boot path was never given the same guard. Because it is the path that runs on a cold start, that is the one that cost the user.

## What it cost

Measured on one cold load, by instrumenting the loader directly rather than inferring from read counts:

- **11** memory extractions (`extractJournalMemoryAtoms` ×5, `extractCheckInMemoryAtoms` ×6)
- **23** loads of `@blackrose_custom_ai_provider` — every extraction resolves the provider config, and with no config saved each one loads, finds nothing and throws
- All 23 arriving through one stack: `extractMemoryAtoms → extractCheckInMemoryAtoms → saveJournalEntryMemories → seedDemoDataForAccount`

Zero of those calls reached the network, because no provider is configured — which is why the cost showed up as storage traffic and boot delay, not as user-visible errors.

## Why run 29's hypothesis was wrong

Run 29 assumed the 23 reads of the provider key matched the 23 keys in `ACCOUNT_PRIVATE_EXACT_KEYS` and blamed the legacy-ownership probe. The number was a coincidence: 23 was the *extraction count* all along. The correct instrument was a stack trace from inside the loader, not a read tally from outside it. **A read count cannot say who read.** That lesson is now in the card for #59.

## The fix

`seedDemoDataIfFirstLaunch` now wraps its worker in the same deterministic-memory scope as `seedDemoData()`.

## Tests

`__tests__/services/seed/seedFirstLaunchDeterministic.test.ts` (3 tests) — the first-launch path had no coverage at all, which is why the gap survived two rounds of investigation. It asserts the seed writes its dataset, writes deterministic atoms, is a no-op on second launch, and **never calls the provider with a configured provider present**.

Sabotage-verified: removing the guard turns *"seeds the dataset without calling the AI provider"* red; restoring it turns the suite green (17/17 across `__tests__/services/seed/`).

## Gates

2036 tests passed, `tsc` 0 errors, lint 0 errors, `check:design` passed.

## Follow-up

The per-route read reduction (29) is smaller than the extraction removal (11 extractions × their own reads) because a *fresh* install only seeds once. The 29 is the steady-state saving on subsequent cold mounts; a true first launch saves more. Card #59 remains open for the unrelated residue (17 `goals` reads, 16 local-memory reads).
