# QA run 68 - 2026-11-09 - a PNG export that needed no dependency (#54)

Round 64.

## The assumption that was wrong

Card #54 was parked with a stated blocker: rasterising needs a native capture
library, so it must wait for a branch allowed to touch the lockfile.

On web there is already a rasteriser: the browser decodes SVG and draws a canvas.

## What shipped

- utils/svgToPng.web.ts: SVG -> Image -> canvas -> PNG data URL at 1080 wide.
  Returns null on any failure (no canvas, decode error, tainted canvas).
- utils/svgToPng.ts (default): returns null, so a phone keeps the SVG it can always
  produce. Null is the contract, not an error.
- PNG is tried first because some chat apps will not preview an SVG at all; the SVG
  stays as the fallback. Both are real files and the writer sees the same sentence.
- downloadDataUrl added beside downloadTextFile: a data URL is already encoded, so
  wrapping it in a Blob would decode and re-encode for nothing.
- The layout module is untouched. The same markup is drawn, never reimplemented.

## Live QA in the real browser

Pressing Share on a real entry produced:

    blackrose-2026-11-09-11-27.png
    data:image/png;base64,iVBORw0K...

Decoded back:

| measure | value |
|---|---|
| size | 1080 x 764 |
| distinct tones | 113 |
| darkest tone | 17 |

113 distinct tones is the point: a blank canvas would be one tone. Real text
rendered.

## Tests

- PNG chosen when the platform can rasterise
- SVG kept when it cannot, instead of failing the export
- 1080 width requested
- an empty entry is refused with a sentence, not an empty file
- filename format changes per format

The rasteriser is mocked because it IS the platform boundary - jsdom has no canvas.
Everything else is the real hook and the real markup builder.
