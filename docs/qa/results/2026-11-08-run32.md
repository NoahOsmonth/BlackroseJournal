# QA run 32 — the memory portrait called tags "themes", and stopped counting at 99

Follows run 31 (Insights counting check-ins as entries). Same class of defect: a number on screen that does not mean what its label says.

## What the screen said

Under the Explore portrait:

> **33 memories · 99 themes · 4 notes**

## What the store actually held

Measured against localStorage on the running app:

| Claim | Reality |
|---|---|
| 33 memories | **33** ✅ (38 stored, 5 retired) |
| 99 themes | **130 distinct tags** ❌ |
| 4 notes | **4** ✅ |

## The two lies

1. **"themes" is a tag count.** `memoryPortraitProse` called `topMemoryThemes(atoms, 99)`, which ranks *distinct tags*. A tag is a keyword the extractor attached to a memory; the app calls them keywords in its own search placeholder ("Search memories, themes, keywords…").
2. **The count was truncated at 99** — a cap chosen for a *list of chips*, reused for a *summary total*. With 130 tags the line silently read 99. There is nothing on screen telling the writer the number is capped, so it looked like a precise fact.

Calling a tag a theme also told the writer their 33 memories contained 99 recurring subjects, which is not a thing that can be true.

## The fix

`memoryPortraitProse` now counts **all** distinct tags (`Number.POSITIVE_INFINITY`, no cap) and labels them **keywords**:

> **33 memories · 130 keywords · 4 notes**

`topMemoryThemes` is unchanged for its real job — the four theme chips beside the portrait still read `topMemoryThemes(atoms, 4)`. Only the summary line changed.

## Verified on the running app

```
PORTRAIT LINE: 33 memories · 130 keywords · 4 notes
```

## Tests

`__tests__/components/memoryPortraitProse.test.ts` (5 tests): counts past the old 99 cap, never says "theme", keeps notes separate, omits the keyword clause when there are none, and describes an empty store without inventing counts.

`__tests__/components/memoryDisplay.test.ts` updated — its fixture asserted `'3 memories · 2 themes · 1 note'`, which is the bug written down as the expected value.

Sabotage-verified: restoring the `99` cap turns *"reports every distinct tag instead of stopping at 99"* red; restoring the new tag count turns it green.

## Gates

2050 tests passed, `tsc` 0 errors, lint 0 errors, `check:design` 188 files passed.

## Pattern worth noting

Runs 31 and 32 both found the same failure shape: **a correct computation under a wrong label**. Neither was a crash, neither appeared in any test, and both survived because the underlying helper was right about what it computed and only the word shown to the user was wrong. Copy-level QA on real data is what catches these; unit tests on the helper cannot, because the helper was never wrong.
