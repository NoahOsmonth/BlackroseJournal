# QA run 73 - 2026-11-09 - the audit could not see what it was auditing (#110)

Round 69.

## The finding

The touch audit covers ten static routes plus entry detail. Three photo surfaces
shipped in the last three rounds and none of them had ever been through it:

- /photos was not in the route list at all.
- The sweep ran against an entry with NO photo, so the photo controls did not exist
  while it measured. The screens came back "clean" because it measured nothing.
- The full-screen viewer is an overlay, not a route, so nothing had ever measured
  what a thumb can reach while it is up.

An audit that reports clean because it measured nothing is worse than no audit: it
manufactures confidence.

## What changed in the audit

- /photos added to the swept routes.
- One entry is given a photo before each pass (and cleared after), so the photo
  controls exist when the sweep runs.
- The viewer is opened and measured as its own row.

## What it found

My own regression from #106:

| control | before | after |
|---|---|---|
| Remove photo | 85 x 23 (defect) | 44 x 44 |
| entry-detail defects | 1 in both schemes | 0 in both schemes |
| entry-detail + viewer | 1 in both schemes | 0 in both schemes |

The button was sized by py-1 alone. Now min-h-11 with centred content.

## Why this counts as evidence

The same screen goes red for the defect and green for the fix. A green result that
was always green proves nothing; this one changed when the code changed.

A source guard stops the padding-only pattern coming back. It is deliberately a
source check: jsdom has no layout, so a Pressable measures 0x0 in Jest no matter
what it says. A render test here would be a test pretending to be a measurement.
