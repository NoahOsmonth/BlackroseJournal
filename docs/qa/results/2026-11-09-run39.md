# QA run 39 — Correcting run 38: the 4x journal reads were a cold-boot burst

Round 33. Web research was unavailable again (`DEEPSEEK_API_KEY` not set), so this round verified the previous round's headline claim against the running app instead of adding a guess on top of it.

## The claim being checked

Run 38 said: *"Today loads the whole journal four times per tab switch — 84 reads, 68 of them journal."* A cache was tried, measured slower, broke backup restore, and was reverted. The layering fix in `useThisWeek` was kept.

## What a real tab switch actually costs

Used the bench's own `pressDockTab` helper, parked on the source tab, then wrapped `Storage.prototype.getItem`:

| Pair | total reads | journal index | journal shards |
|---|---|---|---|
| Threads → Today | 20 | 1 | 16 |
| Archive → Today | 20 | 1 | 16 |
| Insights → Today | 20 | 1 | 16 |
| Today → Threads | 0 | 0 | 0 |

Repeated switches 1..5 gave the same steady-state result: **1 journal load per arrival at Today, 20 reads total**. That is within the "≤25 reads / one load per collection" budget. The shipped bench (`tab-switch-bench.mjs`) was right at 20; it was never undercounting.

## Where the 84 came from

The run-32 probe did this:

```
page.goto('http://localhost:8081/entries', { waitUntil: 'commit' })
waitForTimeout(8000)
manual pointer sequence on elementFromPoint -> Today
```

Reproduced verbatim: **84 reads, 4 index, 64 shards**. Then measured the same page after parking via the dock: still 84, because a cold `/entries` boot had only just happened.

Boot itself, measured on a clean page load:

```
422 total reads
11 journal index reads at ms 28, 29, 34, 36, 38, 40, 136, 419, 419, 419, 419
160 journal shard reads (10 full loads)
```

All four tab screens mount at once on boot, and `seedDemoDataIfFirstLaunch` + `scheduleMemoryRollupsOnAppOpen` also run. So the probe counted the **cold-boot burst**, not a tab switch. Navigating directly to `/entries` and pressing Today within 8 s does not reproduce what a person does after the app has settled.

## The cold-mount bench confirms a separate, real problem

`route-mount-bench.mjs` reads 422 keys on a cold mount, with `goals` 31x, `rosebud_local_memory` 31x, `demo_data_seed_record` 29x. That is a genuine R2/R3 duplication at boot: several hook instances and boot tasks each re-read the same collections. It is NOT a tab-switch defect, and it is not fixed here. The right fix is the shared journal store with a subscription identified in run 38 — one owner, every writer through it, no invalidation discipline to forget. It needs designing, not bolting on, because `localBackup` writes journal keys directly.

## Guard added

`__tests__/qa/tabSwitchBenchWindow.test.ts` guards the measuring tool, not the app. It pins the two facts that keep the bench honest:

1. `startSampling` zeroes `storage.get`, `storage.set` and `storage.keys`.
2. The source tab is pressed and settles for ≥1000 ms **before** `startSampling`, so boot reads fall outside the window.

Sabotage-verified: changing the park delay to `0` turns case 2 red. A third case uses `relPosix` so the guard cannot pass vacuously by matching nothing.

| 10 About | 3 rows; "Crash logs" navigates to /crash-logs |

**No new defect found.** Two apparent failures were QA artefacts, both worth recording:

- **"About Blackrose" / "Privacy Policy" cannot receive clicks** — a `window.alert` from a previous run was still open and blocking the page. Both work once the dialog is accepted; `__tests__/screens/SettingsNotifyUser.test.tsx` already guards them (DEF-009).
- **About rows at x=424, below the window** — the ego browser is a 1248px desktop window; the app centers a 448px column at x=400 and the rows were below the 871px fold. `scrollIntoView` fixed it. Not a layout bug.

API notes learned: `page.on` does not exist in the ego SDK; locators need exact names (`name^=` is invalid); `task.finish()` requires `{ keep: "all" | [...] }`.

## Outcome

The previous round's defect report was wrong and is now corrected in place at `docs/qa/results/2026-11-08-run38.md`. The tab switch was never 4x. The remaining real performance issue is **cold mount** — 422 reads with 30x duplicates on several keys — and it needs the shared-store design, not another cache.
