# QA run 72 - 2026-11-09 - every photo is browsable (#109)

Round 68.

## Why

A photo lives on exactly one entry, so the only way to find one was to remember which
day it was on. The photo thread is now complete: stored (#106), shared (#107),
viewable (#108), findable (#109).

## What shipped

- A Photos screen, newest first, two per row, tap a photo to open its day. Reached
  from Insights beside the other memory surfaces.
- An index key holds id + added-at only, so the grid can order without reading a
  single photo body. Sixty photos would be megabytes to answer a question about
  timestamps.
- The index is written by the same module, under the same lock, as the photos.
- Each cell reads its own thumbnail; the grid never loads a photo it is not showing.
- The account adapter gained getAllKeys, scoped to one account by construction.

## Three real bugs the tests found before commit

1. **Wrong account.** The index write used the global active account id instead of
   the id the bound operation resolved, so it wrote to the wrong place. Every index
   test failed with an empty list.
2. **The prefix strips the @.** Account keys are stored without the leading @, so
   comparing against "@blackrose_entry_photo:" never matched and the repair pass
   silently did nothing.
3. **Trusting an empty disk.** An early return served the index whenever no photo
   keys existed, so rows for deleted photos survived forever. The intersection of
   index and disk is the truth now.

A fourth was a test bug worth naming: the stale-row test deleted the UNSCOPED key,
so it proved nothing until it went through the scoped adapter.

## Self-healing, both directions

- A photo key missing from the index is added back: an index that loses a row must
  not hide a photo the writer can still see on its entry.
- A row whose photo is gone is dropped: the grid must not draw a blank cell.
