# QA run 22 — share an entry as an image (#14)

A share button on any entry turns it into a picture the writer can keep or send.

## How it works

Entry → **share icon** in the header → *"Image saved to your downloads."*

The image is a 1080 px-wide card: the day in small caps, a short rule, the entry text in a serif face, and "Blackrose" at the foot.

## Why an SVG and not a screenshot

- **No native library.** Capturing a React view needs `react-native-view-shot`; drawing it into a canvas needs another. Building the markup directly needs nothing, which matters given this round's other feature (#9) is stalled on exactly that kind of dependency.
- **The output is testable.** A screenshot can only be eyeballed; markup can be asserted byte-for-byte, and the tests do.
- **It never reaches the network.** Built on the device from text that is already on the device.
- **It scales.** A 1080-wide SVG stays sharp on any screen or in any print.

## Live verified

1. Opened **A slow morning with coffee** from the Archive.
2. Tapped *Share this entry as an image*.
3. The screen showed **"Image saved to your downloads."**
4. The produced file was `image/svg+xml`, 1325 bytes, 1080×764.
5. **It parses.** Feeding it to the browser's own `DOMParser` produced **no parser error**, with 8 text elements carrying the real entry:

> `2026-11-08 · 09:47` / `Woke up earlier than usual and` / `just sat with my coffee before the` / `house woke up. Felt calm, almost…`

That last point is the one that matters: it is not a string that merely *looks* like an image, it is a document a renderer accepts.

## What it refuses to do

- An entry with no text reports **"There is nothing in this entry to share yet."** rather than exporting an empty card.
- A very long entry is capped at 40 lines with a "…" — a 2000-word entry would otherwise produce an unreadable 30,000 px strip.
- Text is XML-escaped, so an apostrophe, an ampersand or a stray `<` cannot corrupt the file.

## Colours

Light mode exports on the paper palette, dark mode on the night one, using the app's real hairline token (`#E2DCD2` light / `#2C2A26` dark) — not a black fallback. One test asserts the file never contains `stroke="#000000"`, which is the DEF-033 failure mode in miniature.

## A defect caught by its own test

My first `wrapText` split paragraphs on `/\n+/`, which **collapses a blank line** — so two paragraphs would have exported as one run-on block with no gap. The paragraph test caught it immediately and the fix was `/\n/`. Worth noting because it is invisible until someone writes two paragraphs and exports.

## Not done

- **No PNG.** SVG is what can be produced and verified here without a native dependency. Many chat apps preview SVG; some do not, and that is the case where a PNG would be better. The file name and MIME type would change; the layout code would not.
- **Long entries are truncated**, not continued onto a second image.
- **No preview.** The writer sees a confirmation, not the picture. A preview before saving would be better and is cheap once the markup exists.
- Letter (#11) and weekly recap (#10) cards are not exportable yet; the same builder would serve them.
