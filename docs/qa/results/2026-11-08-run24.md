# QA run 24 — recurring themes across weeks (#25)

Weekly rollups already existed in storage and **no screen read them**. This adds a Today card that surfaces the topics which keep coming back.

## What ships

A 'Keeps coming back' card at the foot of Today:

| State | What the writer sees |
|---|---|
| No weeks written | 'Write for a few more weeks and the things that keep returning will show up here.' |
| Some weeks, not enough | 'Written 2 weeks so far. A few more and…' |
| Enough weeks, no repeats | 'Nothing has come back across weeks yet. That is not a problem — some seasons are wide.' |
| Real patterns | Each topic with its count, e.g. **work stress — 3 weeks** |
| Summaries unreadable | 'Your weekly summaries could not be opened just now. They are not lost — try again in a moment.' |

## Doctrines, each earning its existence

- **Month and year rollups are ignored.** They cover the same days as weeks, so counting both would make a topic look more frequent than it is. A test asserts it.
- **Three weeks minimum.** Two weeks can be a coincidence; `MIN_WEEKS_FOR_PATTERN` is 3 and is stated, not magic.
- **A topic counts once per week** even if a rollup lists it twice.
- **Case and spacing fold together** — 'Work  Stress' and 'work stress' are one theme.
- **Failure is not emptiness.** My first version caught a read error and showed 'write for a few more weeks', telling someone with a year of entries to write more. Split into `needsMoreWeeks` vs `isUnavailable`, with two tests asserting the failure state never shows the 'write more' copy.

## Verified live

- Card renders on Today in the **no-data state** with correct copy.
- Instrumented seeding of week rollups **did not** produce the populated state, so that path is **unproven in the running app**.

## Not proven — and why

I could not get the seeded rollups to appear. What I established:

- Rollup rows and the index **were** present under the current account in the exact key shape the app writes for its own data (`@blackrose_account:v1:<id>:rosebud_memory_rollup:2026-W40`).
- The card kept showing 'write for a few more weeks', i.e. the read returned **zero rows without throwing**, so my `isUnavailable` branch never fired either.
- `listMemoryRollupIndex` swallows a failing `getItem` and returns an **empty index** (memoryRollupStorage.ts line 141), which is exactly indistinguishable from 'no weeks yet'. That is where I ran out of round time.

This is the **third round running** where hand-seeded localStorage fixtures behaved differently from real app writes. The lesson is now firm: **seeded storage is not evidence.** The honest way to prove this card is to let the app write real rollups and then look at the card.

## Follow-up

A card should be opened to prove this with app-written rollups, and to consider making the index read distinguish 'failed' from 'empty' — right now a storage failure is silently reported as 'you have written nothing'.
