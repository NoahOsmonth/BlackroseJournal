01The problem in one picture

The app has two memory stores that never talk to each other. The screen you write on writes to one. The AI's search tool reads the other. So a note you write on Explore is passively visible but not searchable — the AI might happen to have it in context, but it can never go and look for it.

Why the gap is invisible in testing. The note is readable two other ways — it lands in the capsule injected into every chat turn, and search_history can reach it. So recall feels like it works. It's only the dedicated search tool, the one the system prompt tells the model to prefer, that is blind to it. memory_overview would even report userFiles: 0.

03How the AI reads it back

Four read paths reach memory. They differ in whether they fire automatically, what they can find, and how much text they hand the model. The bridge only changes the third one — but that is the one the system prompt tells the model to reach for first.

get_conversation model decides journal entries + check-ins full transcript now finds notes too — they became entries
The design rule that matters most here. User-written notes are returned verbatim and never summarised, and never used to make a claim about the writer. The old panel did exactly the opposite — it concatenated 180 characters of your own text and wrapped it in canned therapy-speak ("Blackrose noticed you often return to themes of…"), with zero model calls behind it. That is the failure mode to design against: an AI asserting something about you, at a moment you didn't ask for it.

04What Dream does, and what it can't promise

Dream is the consolidation pass that promotes staged notes into formal threads. Spec 1 depends on it for topic recall, but the full agent rewrite is spec 3. Worth being precise about now, because the background-execution part of the idea has a hard platform ceiling.

What's achievable

  • Resume after interruption. This is the real guarantee, and it's a property of a durable checkpoint — not of staying alive. It also survives crashes and reboots, which background execution never would.
  • Opportunistic background runs. iOS fetch + processing and Android WorkManager are already wired in this repo — but the only registered task today writes a config snapshot and does no memory work.
  • Read-only UI viewer. A Dream activity surface you can watch and tap into. Straightforward — it reads state, it doesn't drive the run.
  • A 120k budget. Needs to come from the resolved context window, not a constant.

What can't be promised

  • Background work is never guaranteed. iOS gives a refresh task roughly 30 seconds; a processing task gets minutes but only when the OS decides. Frequency is advisory, not a schedule.
  • Force-quit stops everything. On both platforms, until the user relaunches manually. No flag or library changes this.
  • So "it resumes when you open the app" is the honest promise — and the dream acknowledging "I was interrupted, continuing" comes from the checkpoint, not from a live process.

Context numbers, mapped onto what already exists

Your instinct — 120k context, compact around 80k — is close to the existing machinery, which is why I'd reuse it rather than add a parallel scheme:

Note on "copy the chat architecture". The skeleton transfers — tool registry, multi-round loop, live activity, soft-fail. The budgets don't: the chat loop runs 6 rounds inside a 45-second wall clock with a 24k token budget. Dream wants the same primitives with much larger dials, so it's a sibling loop, not a second copy of the same one.

07The one decision that widens an interface

Everything else in spec 1 is contained. This is the piece that reaches code outside the Explore feature, so it's worth seeing before the spec is written.

Memory files carry a type. Today it's 'user' | 'feedback' | 'project'. Notes need one, and there are two ways to give them one:

Reuse 'user'

  • Free: inherits the supersession protection that only type:'user' gets — your own words are never auto-deleted as "restated by a newer memory".
  • Cost: notes would feed the recall user route, the one that fires on "my name / about me / my wife". Your five newest notes get dumped into identity queries and crowd out your actual identity file.

Add 'note'  ← recommended

  • Keeps the user route clean and is semantically honest.
  • And add 'note' to the supersession skip list — that's the property that makes your words undeletable, and today only 'user' has it.
  • Cost: touches MemoryFileType, the listMemoryFiles kind filter, and the memory_list tool schema enum — so toolSchemaPin.test.ts changes deliberately rather than by accident.
